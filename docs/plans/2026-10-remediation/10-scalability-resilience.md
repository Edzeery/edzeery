# 10 — Scalability & Resilience (القابلية للتوسع والصلابة)

> الهدف: رفع النظام من «متجر بحمل معقول» إلى «منصّة متعددة المتاجر تصمد تحت حمل لحظي عالٍ» عبر حلول معيارية (لا ترقيع): تطبيق Stateless، نقل الطبقات الحيّة إلى Redis، قاعدة بيانات للمعاملات فقط، حجز مخزون ذرّي، طوابير موزّعة، وحماية على الحافة.
>
> المصدر: تحليل معماري لهذه الجلسة (فحص فعلي للكود): `CartService`، `InventoryService`، `order-form.blade.php`، `OrderObserver`، `Order::nextOrderNumber`، إعدادات `.env`.
> البوابات: `00-quality-gates.md` (§7، §8).
> **حالة التنفيذ: مخطّطة فقط — لا تبدأ حتى تكتمل المهام الجارية وحتى موافقة صريحة.**
>
> ⚠️ **قاعدة التوقيت:** هذه الخطة تُنفَّذ **فقط** بعد استقرار الشجرة (رفع/إغلاق المهام الجارية) واخضرار مجموعة الاختبارات. تنفيذها فوق شجرة ملوّثة هو أكبر خطر كسر، لا التغيير نفسه.

## 0) لماذا الآن (وأننا ما زلنا في التطوير)

- `APP_ENV=local`، بيانات تجريبية → تكلفة الهجرة شبه صفر الآن (خروج مستخدمين تجريبيين)، ومرتفعة لاحقاً (خروج كل المتاجر، migration على بيانات جارية).
- تحويل مشغّلات التخزين (session/cache/queue) **تغيير إعداد** لا إعادة كتابة، والـRedis مُهيَّأ أصلاً (`REDIS_CLIENT=phpredis`).
- إصلاح سباق المخزون/الترقيم قبل وجود طلبات حقيقية = بلا مخاطرة ترحيل بيانات.

## 1) تصنيف المخاطرة (يحدد ما يُطلق أولاً)

## المرحلة 1 — طبقة Stateless (أكبر مكسب، أقل مخاطرة)

**الجذر:** الجلسة/الكاش/الطابور/الـrate-limit كلها على MySQL (`SESSION_DRIVER=database`, `CACHE_STORE=database`, `QUEUE_CONNECTION=database`) → كل request = كتابة على القاعدة الحيّة.

### SR-01 🟠 P1 — Redis للجلسات
- **الملف:** `config/session.php`, `.env`/`.env.production`, خدمات الجلسة.
- **الإصلاح:** `SESSION_DRIVER=redis`؛ ضبط `session.connection`/`store`. التأكد أن `ResolveStoreFromSubdomain` وسياق المتجر لا يعتمدان على جدول `sessions` مباشرة.
- **اعتبار الهجرة:** تبديل المشغّل يُبطل الجلسات القائمة (خروج مستخدمين) → نفّذه في نافذة، وأعلن للمتاجر التجريبية.
- **قبول:** تتبع جلسة عبر عدة سيرفرات (محلياً: عاملا PHP) يعمل؛ جدول `sessions` يتوقف عن النمو.

### SR-02 🟠 P1 — Redis للكاش
- **الملف:** `config/cache.php`.
- **الإصلاح:** `CACHE_STORE=redis` + بادئة مفاتيح لكل بيئة/متجر حيث يلزم (`edz:`).
- **قبول:** لا كتابة كاش على MySQL؛ TTL يعمل.

### SR-03 🟠 P1 — Redis للـRate Limiter
- **الملف:** كاش الـlimiter (يتبع `cache.default`)، `LoginRequest`, `order-form.blade.php`.
- **الإصلاح:** ضمان أن `RateLimiter` يستخدم Redis (لا DB).
- **قبول:** فحص `RateLimiter::hit` لا يلمس جدول `cache`.

### SR-04 🟠 P1 — طابور Redis + إزالة `--tries=1`
- **الملف:** `config/queue.php`, سكربت `composer dev`, `config/queue.php` (failed_jobs).
- **الإصلاح:** `QUEUE_CONNECTION=redis`؛ إزالة `--tries=1` (استبداله `--tries` مناسب لكل مهمة)؛ ضمان جدول `failed_jobs`؛ **قبل التبديل:** تجفيف طابور database (drain) حتى لا تُفقد مهام أثناء الانتقال.
- **قبول:** مهام قديمة نُفّذت، لا مهمة تُفقد عند فشل عابر.

## المرحلة 2 — طبقة البيانات

### SR-05 🟠 P1 — Connection Pooler
- **الإصلاح:** ProxySQL (MySQL) بين التطبيق والقاعدة؛ ضبط `max_connections` واقعياً؛ نموذج PHP = اتصال لكل عملية.
- **قبول:** لا «Too many connections» تحت حمل النموذج المحدد.

### SR-06 🟠 P1 — Read Replica + فصل القراءة/الكتابة
- **الملف:** `config/database.php` (`read`/`write`).
- **الإصلاح:** قراءات كتالوج الفرونت ستور واللوحات التحليلية → replica؛ الكتابات (طلبات/مخزون) على الـprimary.
- **اعتبار:** تأخير النسخ (replication lag) في مسارات القراءة-بعد-الكتابة → استخدم sticky للـprimary عند الحاجة.
- **قبول:** زمن استجابة عرض المنتجات ينفصل عن حمل الكتابة.

### SR-07 🟠 P1 — إصلاح مولّد رقم الطلب (يمدّ ملاحظة STATUS/revert)
- **الملف:** `app/Models/Orders/Order.php:300-310`, `app/Observers/OrderObserver.php:216-226`.
- **الجذر:** `MAX(number)+1` مع `lockForUpdate` على `CAST(...)` → مسح + قفل نطاق المتجر + خطر duplicate على `unique(store_id,number)`.
- **الإصلاح المعياري:** جدول `store_sequences(store_id, next_value)` بزيادة ذرّية، أو `auto_increment` مقيّد بالمتجر، أو معرّف نظام ULID/UUIDv7 ورقم عرض مشتق.
- **قبول:** اختبار تزامن: 1000 طلب متزامن لنفس المتجر → صفر duplicate، صفر deadlock، صفر تسلسل كامل.

### SR-08 🟡 P2 — فهارس تُستغَل فعلياً
- **الملف:** cross-ref `P-04` + `M-03`؛ احذف/أعد صياغة أي predicate دالي يمنع استخدام الفهرس (`CAST`).
- **قبول:** `EXPLAIN` يستخدم الفهرس على مسارات الطلبات/المخزون/التتبع.

## المرحلة 3 — التزامن (مسار الفلوس، بعناية)

> يمدّ `M-02` (الحجز الذرّي على مستوى DB) ويرفعها إلى نموذج قابل للتوسع.

### SR-09 🔴 P0 — حجز المخزون الذرّي لحظة الطلب
- **الملف:** `resources/views/livewire/storefront/order-form.blade.php:465-471`.
- **الجذر:** قراءة بلا قفل (`$available = (int)$variant->stock`) ثم إنشاء الطلب → بيع زائد على الطلبات المعلّقة؛ الخصم الحقيقي متأخر عند التأكيد (`OrderObserver`).
- **الإصلاح (أساسي):** `UPDATE product_variants SET stock = stock - q WHERE id = ? AND stock >= q` → affected rows = 1 نجاح / 0 نفاد. داخل نفس transaction الطلب.
- **قبول:** اختبار تزامن: خيطان على آخر قطعة → واحد فقط ينجح، لا stock سالب، لا طلب بلا رصيد.

### SR-10 🟠 P1 — مفتاح Idempotency للـcheckout
- **الإصلاح:** `checkout_token` واحد لكل جلسة/محاولة، يمنع الطلب المزدوج عند الضغط/إعادة الإرسال (وهذا يحلّ شقّ «10 refresh»).
- **قبول:** إرسال متزامن بنفس التوكن → طلب واحد فقط.

### SR-11 🟡 P2 — حجز قابل للتوسع (Flash Sale)
- **الإصلاح (عند الحاجة لحمل استثنائي على منتج واحد):** عدّاد Redis ذرّي (`DECRBY` + سكربت Lua) كحجز مؤقت + مطابقة غير متزامنة إلى DB؛ الـDB يبقى مصدر الحقيقة.
- **قبول:** نافذة تخفيضات على منتج واحد لا تُسقط الـprimary؛ المخزون النهائي متطابق.

## المرحلة 4 — اللامتزامن والطوابير

### SR-12 🟠 P1 — Horizon + عوامل متعددة
- **الإصلاح:** تثبيت `laravel/horizon`؛ عدة عمال؛ طوابع زمنية؛ أفضلية طوابير؛ مراقبة العمق والفشل.
- **قبول:** عمق الطابور يبقى قريباً من الصفر تحت حمل اختبار.

### SR-13 🟠 P1 — `timeout`/`tries` لكل مهمة (يمدّ O-07)
- **الملف:** `app/Domains/Order/Jobs/*`, `app/Domains/Shipping/Jobs/*`, `app/Services/InvoicePdfService.php:31`.
- **الإصلاح:** `public $timeout` و`public $tries` حسب نوع العمل؛ `failed_jobs` مُراقَبة بتنبيه.
- **قبول:** مهمة تفشل عابرة تُعاد وتنجح؛ مهمة تفشل دائماً تُعمَّر في failed_jobs بلا فقدان صامت.

### SR-14 🟡 P2 — إخراج العمل الثقيل كلياً من مسار الطلب
- **الإصلاح:** الإشعارات، إيميل، PDF، مزامنة الشركة → async. رد الشراء: أنشئ → dispatch → ارجع.
- **قبول:** زمن استجابة الشراء لا يتضمن أعمال الشركة/PDF.

## المرحلة 5 — الحافة والحماية

### SR-15 🟠 P1 — CDN/WAF أمام الـstorefront
- **الإصلاح:** Cloudflare (أو مكافئ) لامتصاص L7 DDoS/البوتات + تخزين مؤقت أصول ثابتة + حماية فتحات الشراء.
- **قبول:** حمل اصطناعي كبير لا يصل للـprimary (يُصفّى عند الحافة).

### SR-16 🟠 P1 — Full-page cache لصفحات الكتالوج العامة
- **الإصلاح:** كاش صفحات المتجر العامة (خارج الجلسة/السلة) على الحافة/Redis مع فواصل cache-tags لكل متجر.
- **قبول:** TTFB لصفحة المنتج ينخفض بشكل حاد تحت حمل قراءة.

### SR-17 🟠 P1 — Rate limit متعدد المفاتيح في Redis (يمدّ O-02/O-03)
- **الإصلاح:** مفتاح مركّب (متجر + IP + مسار/حساب) + token bucket؛ لا `per-IP` فقط.
- **قبول:** 10k IPs مختلفة لا تُسقط النظام؛ جهاز واحد مسيء يُقيَّد.

### SR-18 🟡 P2 — TrustProxies صحيح (يمدّ O-03)
- **الإصلاح:** قائمة CIDR للـLB/CDN بدل `at: '*'`، وإلا فالـIP في الـrate limit قابل للتسميم.
- **قبول:** `X-Forwarded-For` مزوَّر لا يغيّر مفتاح الحد.

## المرحلة 6 — إنتاجية وقت التشغيل

### SR-19 🟠 P1 — Laravel Octane
- **الإصلاح:** تشغيل على Swoole/RoadRunner (+ Redis للـcache/session مطلوب مسبقاً) لإزالة تكلفة bootstrap لكل request.
- **تحذيرات:** تسرّب الحالة بين الطلبات (singletons/static) — مراجعة `StoreContext` و`currentStoreId` للتأكد من عدم بقاء حالة بين الطلبات.
- **قبول:** اختبار حمل يظهر مضاعفة RPS بلا تغيير منطق؛ لا تسرّب سياق متجر بين الطلبات.

### SR-20 🟡 P2 — OPcache + ضبط PHP-FPM
- **الإصلاح:** OPcache مُفعّل ومقاس؛ ضبط `pm`/`max_children` حسب الذاكرة والـpooler.
- **قبول:** لا طوابير انتظار طويلة ولا OOM.

## المرحلة 7 — توسّع المتاجر (Tenancy at scale)

> المبدأ: منع Noisy Neighbor قبل عزل الـDB.

### SR-21 🟠 P1 — طوابير ومعدلات منفصلة لكل متجر
- **الإصلاح:** طابور/أولوية لكل متجر (أو buckets)؛ حد لكل متجر على الحمل.
- **قبول:** حمل متجر واحد لا يؤخر طوابير بقية المتاجر.

### SR-22 🟡 P2 — مسار عزل تدريجي
- **النمط التنازلي المعياري:** مشترك `store_id` (الحالي) → **schema لكل متجر** → **DB لكل متجر (Shard)** مع `Tenant-aware connection resolver`.
- **تفعّله عندما:** كتابات DB تجاوزت قدرة العقدة، أو متجر واحد يشوّش، أو متطلب عزل/امتثال.
- **قبول:** سيناريو ترحيل متجر واحد إلى DB مستقل موثّق ومُختبر (dry-run).

## المرحلة 9 — الصلابة والاستمرارية

### SR-26 🟠 P1 — تدهور رشيق
- **الإصلاح:** ماذا يحدث لو سقط Redis/الطابور/خدمة الشحن؟ مسارات بديلة، رسائل واضحة، لا 500 صامت.

## قبول المرحلة (METRICS)

- [ ] الجلسات/الكاش/الطابور لم تعد على MySQL.
- [ ] صفر duplicate في رقم الطلب تحت تزامن، وبلا `MAX+1`.
- [ ] آخر قطعة تحت تزامن: نجاح واحد فقط، لا stock سالب.
- [ ] لا «Too many connections» تحت حمل النموذج.
- [ ] TTFB: الكتالوج `< 300ms`، الطلب (acceptable under load) `< 800ms`.
- [ ] تقرير اختبار حمل قبل/بعد لكل مرحلة في `STATUS.md`.

## قواعد التنفيذ الصارمة

1. **لا Big Bang** — مرحلة واحدة، خطوة واحدة، تراجع مستقل.
2. **launch** على staging أولاً؛ إطلاق تدريجي/خلف flag.
3. كل تغيير: `pest` قبل/بعد + `pint` + تحديث `STATUS.md`.
4. مسار الفلوس: لا إطلاق بلا اختبار تزامن مخصّص.
5. **لا تلمس `.env` الحقيقي** ولا تُدخل أسراراً؛ وثّق في `.env.example`.
6. قبل أي migration: نسخ احتياطي مُختبر.
